# Suporte no site — plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Disponibilizar atendimento entre instituições/professores e suporte global, com anexos privados, conversa ao vivo, notas internas e fecho definitivo.

**Architecture:** Módulo Support no monólito existente, com autorização única para HTTP, downloads e SignalR. HTTP persiste as operações; SignalR apenas sinaliza alterações confirmadas e o cliente volta a ler a API. SQL, quota e auditoria partilham uma transação; armazenamento privado de ficheiros usa preparação e compensação.

**Tech Stack:** .NET 10, ASP.NET Core, Oracle EF Core/MySQL 8, Blazor WASM, xUnit; cliente oficial SignalR 10.0.13, mínimo corrigido para GHSA-334f-vvp4-7g6p. Sem serviço externo de chat. MAUI conserva o comportamento atual nesta entrega.

**Spec:** `docs/superpowers/specs/2026-10-13-support-design.md`, incluindo a revisão após PR #6. Plano pendente de revisão do utilizador; ainda sem execução.

## Global Constraints

- Apenas Teacher/InstitutionAdmin criam pedidos. Teacher vê os próprios; InstitutionAdmin os da instituição. Student não tem acesso.
- PlatformAdmin requer `support.read`/`support.manage`; só master delega. `support.manage` exige `support.read`. Não conceder automaticamente aos restantes administradores.
- Estados `Open`, `InProgress`, `AwaitingClient`, `Closed`; fechado é terminal. Mensagem pública do cliente em `AwaitingClient` regressa a `Open`.
- Assunto 150, texto 4000, resumo de fecho obrigatório até 1000 caracteres. Descrição inicial não vazia. Mensagens seguintes exigem texto ou anexo.
- JPEG/PNG/WebP/PDF/TXT/DOCX/XLSX/PPTX; até 5 MiB/ficheiro, três por mensagem, 15 MiB no total; corpo multipart até 16 MiB. Quota institucional inicial 100 MiB configurável.
- Sem notas/ficheiros internos nos DTOs, avisos ou downloads escolares. Sem rotas estáticas para anexos, edição de mensagens, reabertura ou eliminação do histórico.
- Não usar dados pessoais/online nas suites. Segredos e diretórios privados ficam fora do Git. Interface/documentação em português e textos em recursos.
- Desenho/paleta atuais; desktop e 390 px, teclado/foco, mensagens de falha recuperáveis. Duração de desenvolvimento não é critério de planeamento.
- Uma tarefa de cada vez, com TDD e revisão antes de seguir. Só publicar após CI e revisão por colega; não alterar a demonstração durante a implementação.

Todos os métodos I/O abaixo recebem `CancellationToken ct`. IDs são `int`; versões `long`; datas UTC `DateTime`; `clientId` é `Guid`. Models de Application não referenciam Contracts.

Interfaces produzidas pelas tarefas:

- `SupportActor(int Id, string Name, string Role, int? InstitutionId, bool CanReadGlobal, bool CanManageGlobal)`; `SupportAuthorization.ResolveAsync(ct): Task<SupportActor>` revalida a conta via `IIdentityStore` e o contexto global via `IPlatformAdminDirectory`/`PlatformAuthorization`. Não aceita um ator arbitrário nos endpoints.
- `AuthorizedSupportScope`: classe imutável com construtor interno de Application, criada pela autorização para uma operação/leitura. Contém ator, âmbito escolar/global e visibilidade permitida; não é um `ICurrentAccount` falso.
- `SupportTicketQuery(int Page=1, int PageSize=20, string? Search=null, string? Status=null, string? Priority=null, int? InstitutionId=null, int? AssigneeId=null)`; validar `Page>=1`, tamanho 1..100. Escolar não escolhe outra instituição.
- `SupportService.CreateAsync(CreateSupportTicket command, ct): Task<SupportTicketResult>`; `SendAsync(int ticketId, SendSupportMessage command, ct): Task<SupportMessageResult>`; `UpdateAsync(int ticketId, UpdateSupportTicket command, ct): Task<SupportTicketResult>`; `CloseAsync(int ticketId, CloseSupportTicket command, ct): Task<SupportTicketResult>`.
- `CreateSupportTicket(Guid ClientId, string Subject, string Category, string Priority, string Description, IReadOnlyList<IncomingAttachment> Files)`; `SendSupportMessage(Guid ClientId, long RowVersion, string Text, bool Internal, IReadOnlyList<IncomingAttachment> Files)`; `UpdateSupportTicket(long RowVersion, string Status, string Priority, int? AssigneeId)`; `CloseSupportTicket(long RowVersion, string Summary)`.
- `SupportQueries.ListAsync(SupportTicketQuery query, ct): Task<SupportTicketPage>`; `GetAsync(int ticketId, ct): Task<SupportTicketResult>`; `MessagesAsync(int ticketId, int? BeforeId, int? AfterId, int Take, ct): Task<SupportMessagePage>` (Before/After mutuamente exclusivos; Take 1..50); `DownloadAsync(int attachmentId, ct): Task<SupportDownload>`.
- `ISupportStore`: `ListAsync(scope,query,ct)`, `FindTicketAsync(scope,id,ct)`, `ListMessagesAsync(scope,ticketId,beforeId,afterId,take,ct)`, `FindMessageByClientIdAsync(scope,ticketId,clientId,ct)`, `FindTicketByClientIdAsync(scope,clientId,ct)`, `FindAttachmentAsync(scope,id,ct)`; retornos correspondem aos models acima, com nulável nas pesquisas individuais. `AddTicket(SupportTicket ticket)` e `AddMessage(SupportMessage message)` preparam entidades; `ReserveBytesAsync(scope,long bytes,long limit,ct)` reserva quota atomicamente.
- `ISupportUnitOfWork.ExecuteAsync<T>(AuthorizedSupportScope scope, Func<CancellationToken,Task<T>> operation, ct): Task<T>`: ativa escrita restrita a Support e auditoria, faz commit, traduz conflitos para `SupportException`; não reutiliza a tradução `AccountExists` administrativa.
- `IncomingAttachment(string FileName, Stream Content)`; `PreparedAttachment(string StorageKey,string FileName,string ContentType,long Size,string Sha256)`; `IFileStorage.PrepareAsync(IncomingAttachment file,ct)`, `CommitAsync(PreparedAttachment file,ct)`, `DeleteAsync(string key,ct)`, `OpenReadAsync(string key,ct)` com retornos `Task<PreparedAttachment>`, `Task`, `Task`, `Task<Stream>` respetivamente. Application não recebe caminhos absolutos.
- `ISupportNotifier.ChangedAsync(int ticketId, bool internalOnly, ct): Task`; após commit, falha deste aviso não transforma envio persistido em falha HTTP.

DTOs têm os mesmos campos funcionais dos comandos, mas não expõem `Stream`, caminhos, hashes de credenciais ou entidades EF. `SupportTicketResponse` inclui Id/InstitutionId/AuthorId/AuthorName/Subject/Category/Priority/Status/AssigneeId/AssigneeName/RowVersion/CreatedAt/ClosedAt/ClosedBy/CloseSummary e capacidades `CanReply`/`CanManage`/`CanClose`. Resposta escolar de mensagem inclui Id/ClientId/AuthorId/AuthorName/Text/CreatedAt/Attachments; a administrativa acrescenta `Internal`. `SupportAttachmentResponse` inclui apenas Id/FileName/ContentType/Size. Model de leitura separa `PublicMessages` e `InternalMessages`, filtrando antes da projeção; escolar nunca recebe o segundo. A tarefa 2 define os retornos completos destes models nos ficheiros `SupportModels.cs`/`SupportResponses.cs` antes de implementar os consumidores.

## Review Focus

Estes casos devem constar expressamente dos testes das tarefas indicadas; não ficam cobertos só pelo percurso feliz:

1. Replay após timeout versus chat entretanto fechado: devolver o envio já aceite sem duplicação, mas recusar novo envio (tarefas 2/3/5).
2. Fecho concorre com resposta e quota concorre entre pedidos distintos: só a operação permitida vence, sem ultrapassar espaço nem deixar mensagem parcial (tarefas 2/3/8).
3. Permissão/suspensão muda após inscrição no chat: destinatário perde acesso a HTTP/download/hub e a avisos subsequentes (tarefas 2/4/8).
4. Nota interna altera uma versão que o professor já leu: 409 conserva o rascunho, sem expor nota/anexo/contagens internas (tarefas 4/6/7).
5. API confirmou envio mas SignalR/rede falha e sessão muda: preservar confirmação, recuperar pelo cursor e limpar a sessão anterior (tarefas 4/5/7).
